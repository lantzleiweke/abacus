# Abacus 0.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Abacus good at reviewing and auditing what agents did, adjusting the context they work from, and handing work back, without the `bd` CLI: human gates for review and plan approval, a Needs me view, history with a safe restore, project memories, the editing gaps, and live updates on Beads 1.3.

**Architecture:** Same shape as 0.1: a sandboxed Preact panel talks only to the Node service through `host.serviceRequest`; the service shells out to `bd` and keeps a per-project snapshot. 0.2 adds (a) snapshot fields derived from the export the service already reads (gates, leases, capabilities), so Needs me renders from one snapshot, (b) on-demand routes for history, memories and the new writes, all through the per-root queue and re-read-before-write path, and (c) an optional events-journal follower that only nudges the existing refresh.

**Tech Stack:** unchanged (TypeScript 5, Preact 10, esbuild, Vitest, `@openchamber/sdk` 2.3.2). No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-14-abacus-0.2-design.md` (binding). Contracts: `docs/bd-cli-contract.md` (including "bd 1.3.1 differences" and "bd 1.3.1 capabilities for 0.2", written by Task 1), `docs/sdk-contract.md`. Fixtures: `test/fixtures/bd13/`. Executors read the spec, both contracts and the fixtures named in their task first.

## Global Constraints

Copied from the spec. They bind every task.

- bd 1.3.1 is the primary target; bd 1.2.2 keeps working for everything 0.1 does; Phase 0 (the 1.3.1 fixes, a separate lane) is not re-planned here.
- Never `--force`. Never `bd config set` without the user pressing a button that says what it will do.
- Copy rules: no em dashes; "Beads" the product versus "beads" the issues; no CLI words (pull, push, remote, dolt) in the UI.
- Sandbox: the panel frame has `allow-scripts` only. No `<form>`, no submit, no popups, no modals. A guard test exists (`test/unit/panel/sandbox.test.ts`) and must keep passing.
- Build on a `feat/0.2` branch in a worktree (create it before Task 2; the main checkout keeps running the installed extension). Never run `bd` in a real project: scratch projects only, under the OS temp dir or `~/.cache/openchamber-beads-scratch/`.

Carried over from 0.1 (still binding, they are what the spec means by "all 0.1 anti-goals stand"): every panel write passes `--actor "<git user.name> (panel)"` and goes through the per-root queue; never edit config files except through the one explicit button in Task 9; never run `bd show`; never push except from the user's Publish; reads use `--readonly`.

## Review Focus

Five ways this work fails while still passing "does it run". Each has a named test in the owning task.

1. **Undo overwrites newer work.** Restore must be refused, with the current value shown, when the field changed after the change being undone. Tests: Task 5 (`restore is refused when the field moved on`, `restore passes expected = the value the change produced`), Task 13 (`refused restore shows the current value and writes nothing`).
2. **An agent resolves a gate while the panel is open.** The row must disappear on the next snapshot, a Resolve click that loses the race must report who resolved it (not a raw error), and Activity must say so. Tests: Task 2 (`resolved gate leaves the gates list`), Task 3 (`resolve on an already resolved gate is a conflict naming the resolver`, `agent-resolved gate gets an Activity row flagged`), Task 11 (`row disappears when the gate resolves`).
3. **Memories edited concurrently.** An edit or a forget must re-read first and refuse when the stored text differs from what the page showed; a forget is never one click. Tests: Task 6 (`edit refused when the text changed since load`, `forget refused when the text changed`, `remember with an existing key never silently recalls`), Task 14 (`forget needs the confirm step with the text shown`).
4. **The events follower dies, hangs or outlives its use.** The panel must keep working by polling, the follower must stop when nobody is looking and must not leak past the service. Tests: Task 8 (`falls back to polling when the follower exits`, `backs off and gives up after repeated failures`, `stops after the panel goes quiet`, `kills the child on service shutdown`, `kills stale followers on start`).
5. **bd 1.2.2 (or any bd) without a command.** A missing command must show as "not available in this version of Beads", hide the feature, and never break the panel. Tests: Task 2 (`capabilities are off below 1.3`), Task 3 (`unknown command maps to unsupported`), Task 9 (`live updates are hidden without the capability`), Task 10 (`unsupported hides the entry points`).

Also covered, because the Task 1 capture showed they bite: a `human`-labelled bead that is already closed (Task 4, Task 11), a gate row leaking into counts, Epic, Status or Activity (Task 2), duplicate `bd history` rows (Task 5), a memory key `schema_version` or text equal to a key (Task 6), a clock-local date parse preview that disagrees with bd (Task 15).

## What Task 1 found that changes the design

The spec left these to the builder; the captures settle them. Each is recorded as a Ruling in `docs/decisions.md` by Task 17.

- **Derive, do not call, for the per-poll sets.** Gates, the human set, the stale set and the eligible-epic set are all computable from the export the service already reads every refresh. Calling `bd gate list`, `bd human list`, `bd stale` and `bd epic status` on every poll would add four process starts per refresh for no new information (and `bd stale --days 0` is an error). So the snapshot gains `gates` and `leases`; the human, stale and eligible sets are computed in the panel from `beads`. Integration tests prove each derived set equals the bd command's answer on a scratch project. The spec's `gates`, `human`, `stale`, `epicEligible` routes are therefore not built.
- **`bd history` is one row per database commit, with no actor and no labels.** The route dedupes consecutive identical snapshots, joins `--events` on `created_at == updated_at` for the actor and for label changes, and caps and pages.
- **`bd memories` has no timestamps.** "Newest first" comes from `dolt_diff_config` through the existing `runSql`.
- **Three commands print text, not JSON** (`gate resolve`, `human respond`, `human dismiss`): success is the exit code plus a re-read.
- **`bd defer <id>` with no date keeps an existing date.** "Defer indefinitely" is `undefer`-then-`defer`, or `update --defer ""` then `defer`; "Undefer" is `bd undefer`.
- **No dry run for dates.** The preview uses a small parser of the common forms and says "Beads will read this" for anything else.
- **`bd config set events-journal true` edits the tracked `.beads/config.yaml`.** The button copy must say so.
- **A closed gate's `blocks` edge persists.** "Gated" means an edge to a gate whose status is not closed.

**Interfaces:**
- Produces (types the whole plan uses; declare all route names in `api.ts` now, with stub request/response types, so later tasks only fill handlers):

```ts
type Capabilities = { liveUpdates: boolean; leases: boolean };      // both true only for bd >= 1.3.0
type GateKind = 'human' | 'timer' | 'gh:run' | 'gh:pr' | 'bead' | string;
type Gate = {
  id: string; kind: GateKind; reason: string | null;               // text after "\n\nReason: " in the gate's description
  blocks: string[];                                                 // bead ids with an edge to this gate (ids still in the export)
  createdBy: string | null; createdAt: string; timeoutMs: number | null; // timer gates: nanoseconds / 1e6
  /** Plan approval: kind human and reason starts with PLAN_APPROVAL_REASON. */
  planApproval: boolean;
};
type Lease = { beadId: string; holder: string; expiresAt: string };  // ISO UTC
// SnapshotResponse (unchanged: false) gains:
//   capabilities: Capabilities; gates: Gate[]  /* OPEN gates only */; leases: Lease[]
// WriteErrorCode and ApiErrorCode gain 'unsupported'.
// ChangeKind gains 'gate_opened' | 'gate_resolved' (used by Task 3).
export const PLAN_APPROVAL_REASON = 'Approve the plan before work starts';
export const REVIEW_REASON = 'Review before closing';
```

- Rules:
  - **Gate rows are removed from `beads` before anything else sees them** (diff, counts, unseen, activity, Epic and Status inputs, `readyIds`). Do it once, where the export is applied in `exportAndApply`, via `splitGates(beads): { beads, gateRows }`. Keep the edge on the blocked bead's `dependencies` as exported; the panel hides edges to gates in Relationships (Task 12).
  - `gates` is every non-closed gate row, with `blocks` taken from the other beads' `blocks` edges to it. A closed gate is not listed (its edge persists in the export, which is why "gated" is decided on the gate's status, never on the edge alone).
  - `leases` is read with the existing `runSql` (`SELECT issue_id, holder, lease_expires_at FROM leases`) only when `capabilities.leases` and at most once per minute per root (it rides the same cadence as the minute export). Any read failure gives `leases: []` and never an error banner.
  - `capabilities` comes from the `bdVersion` already in workspace detection (`compareVersions`). Both fields are part of `dataKey`, so a change reaches the panel.
  - Gates and leases are part of the cursor digest.
- Consumes: `RootCache`, `exportAndApply`, `respond`, `dataKey` in `snapshot.ts`; `runSql` in `bd/audit.ts`.

- [ ] Tests (unit): `capabilities are off below 1.3`, `capabilities are on at 1.3.1`; `gate rows never reach beads, counts, unseen or activity` (use `test/fixtures/bd13/export-with-gate.*`); `gates lists only open gates with their blocked beads`; `resolved gate leaves the gates list` (a closed gate row with its edge still on the bead); `reason is read after the Reason marker, null when absent`; `plan approval is a human gate with the known reason`; `a timer gate carries its timeout`; `leases read failure gives an empty list, no error`; `gates and leases change the cursor`.
- [ ] Integration (`BD_INTEGRATION=1`, scratch project): the derived `gates` equals `bd gate list --json` (treat `null` as `[]`); a gate resolved through bd drops out.

```ts

type GateCreateRequest = DirectoryRequest & { id: string; reason: string; kind?: 'human' };          // default reason REVIEW_REASON; plan approval passes PLAN_APPROVAL_REASON
type GateCreateResult = { ok: true; gate: Gate } | { ok: false; code: 'already-open'; gate: Gate };
```

- Rules:
  - `gate create --type=human --blocks <id> --reason <r> --json -- ` (user text after `--` where bd allows it; reason is a flag value so quote it as one argv element). Reason is trimmed, 1 to 500 chars, no newlines. The id and the bead must exist and not be closed (re-read through the export, never `show`).

  - A bd "unknown command" or "unknown flag" failure on any new command maps to `WriteError('unsupported', 'This version of Beads does not support that.')`. Add the pattern once in `writeFailure` so Tasks 4 to 7 inherit it.
  - **Gate Activity:** the diff compares the previous and current open-gate sets and emits `gate_opened` (reason, blocked bead) and `gate_resolved` (reason, blocked bead, `actor` from the audit `closed` event on the gate, null when unknown). `ChangeEvent.byPanel` is true only for an exact match with the panel actor. When the actor is known and is not the panel actor, the event carries `flag: 'resolved-elsewhere'`; the text the panel shows is built in Task 13 ("Review gate resolved by Claude Code"). A gate opened or resolved by the panel auto-sees like any other panel write. First open of a project does not flag existing gates (baseline, as in 0.1).

### Task 5: History route and restore (fixer)

**Files:** Create `src/service/history.ts`. Modify `src/service/routes.ts`, `src/shared/api.ts`, `src/service/bd/adapter.ts` (`BdProvider.history`). Test `test/unit/service/history.test.ts` (fixtures `test/fixtures/bd13/history.json`, `history-events.json`), `test/unit/service/writes.test.ts` (extend), `test/integration/history.test.ts`.

**Interfaces:**
- Produces:

```ts
type HistoryChange = { field: string; from: JsonValue; to: JsonValue; text: boolean };   // text: description/design/acceptance/notes (long text, the panel shows a compact diff)
type HistoryEntry = { id: string; at: string; actor: string | null; changes: HistoryChange[]; restorable: string[] /* fields, see rules */ };
type HistoryRequest = DirectoryRequest & { id: string; before?: string /* entry id, for the next page */; limit?: number /* 1..50, default 20 */ };

```

- Rules:
  - Read `bd --readonly history <id> --json` with `--limit 200` and, on 1.3, `--events`. Read on demand only (when the panel opens the section), never from the refresh loop.
  - **Dedupe**: drop a snapshot identical (by field values) to the one before it; the 12-rows-for-4-changes case in the fixture gives 4 entries. Diff each snapshot against the next older one; the oldest has no predecessor and is shown as "Created".

The service already refuses (`conflict` with the current bead) when the field no longer holds `to`.
  - Paging cursor is the entry id (`<hash>:<index>`); the page never splits one entry.
- Consumes: `bd/exec.ts`, `bd/parse.ts` helpers, `stillAsShown` in `adapter.ts`.

- [ ] Tests: `consecutive identical snapshots collapse` (fixture); `entries are newest first with from and to`; `actor joined on updated_at, null when unmatched`; `label changes come from events only`; `events unreadable gives labelsKnown false`; `missing id gives an empty list`; `paging does not split an entry`; `restore passes expected = the value the change produced`; `restore is refused when the field moved on` (a later change to the same field: result is `conflict` with the current bead, nothing written); `restore of one field does not touch the others`; `a text field is restored or refused as a whole` (the field is the unit: a later edit anywhere in it refuses the restore).

### Task 6: Memories (fixer)

**Files:** Create `src/service/memories.ts`. Modify `src/service/routes.ts`, `src/shared/api.ts`. Test `test/unit/service/memories.test.ts` (fixtures `memories-list-json`, `remember`, `remember-update`, `remember-bare-key`, `forget`, `forget-missing`, `memories-empty`), `test/integration/memories.test.ts`.

**Interfaces:**
- Produces:

```ts
type Memory = { key: string; text: string; changedAt: string | null; changedBy: string | null };   // newest first
type MemoriesRequest = DirectoryRequest & { query?: string };
type MemoriesResult = { memories: Memory[]; fingerprint: string };   // fingerprint covers keys and texts, for the stale-page check
type RememberRequest = DirectoryRequest & { text: string; key?: string; expectedText?: string | null; fingerprint: string };
type ForgetRequest = DirectoryRequest & { key: string; expectedText: string };

```

- Rules:
  - List: `bd memories --json`, drop `schema_version`, then order and annotate with one `runSql` (`dolt_diff_config`, the query in the contract) for the last change per key and its actor (from the commit message `bd: remember|forget (auto-commit) by <actor>` via `dolt_log`). A key with no diff row sorts last and has `changedAt: null`. SQL failure never fails the list: alphabetical, no dates.
  - Always pass `--key`: generate one from the text (lowercase, words joined by `-`, 60 chars max, `-2`, `-3` on collision) when the person gives none. **Reject** a key equal to `schema_version` or failing `/^[a-z0-9][a-z0-9._-]{0,79}$/`. Treat `action: "recalled"` in the answer as a failure (`failed`, "Beads did not save that"), because `remember "<existing key>"` without `--key` recalls.
  - **Add**: refuse (`changed`, with the current memory) when the key already exists and `expectedText` is not set (the form chose Add, not Edit). **Edit**: re-read the key; refuse with `changed` unless the stored text equals `expectedText`. **Forget**: re-read; refuse unless stored text equals `expectedText`; a missing key is `changed` with `current: null` (someone already forgot it).
  - Text 1 to 4000 chars (the spec's anti-goal is losing a memory, not truncating one: reject longer text, never cut it).
  - All writes run in the per-root queue with the panel actor. Embedded and server mode both work (`runSql` handles both); the history of a memory is read by Task 14 through the same list call, so no extra route.
- Consumes: `runSql`, `withRootQueue`, `writeFailure`.

- [ ] Tests: `list drops schema_version and orders newest first`; `list survives a failing SQL read`; `key is always passed to remember`; `generated key avoids collisions`; `rejects the key schema_version`; `remember with an existing key never silently recalls` (answer `recalled` is a failure); `add refuses an existing key without expectedText`; `edit refused when the text changed since load`; `forget refused when the text changed`; `forget of an already forgotten key reports changed with null`; `text over 4000 is rejected, not cut`; `search filters by key and text`; route validation.
- [ ] Integration: remember, edit, forget in a scratch project, in embedded mode; the list shows the right order and `changedBy` is the panel actor.
