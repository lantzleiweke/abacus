# Abacus 0.2: design

Status: draft for review, 2026-10-14. The user asked for the spec straight from what was agreed in conversation, without a question round. Items marked **my call** are mine and open to change.

## Intent

Abacus 0.1 lets a person see and edit agent-created beads from OpenChamber's right rail. 0.2 makes it good at the job it exists for: **review and audit what agents did, adjust the context they work from, and hand work back**, without the `bd` CLI.

Evidence behind the scope: `docs/backlog.md` (39 items from a Beads feature inventory, 22 agent task tools and other Beads GUIs). The user chose the Beads capabilities Abacus does not expose yet, with human gates as the shared base for review and plan approval, plus live updates on Beads 1.3.

## The user's job (unchanged from 0.1)

The user does not use the `bd` CLI. Agents create and change beads; the user reviews and audits them, adjusts their context, and sends beads to the agent. Built for the user first, public later (the repo is public now). Works across all of the user's Beads projects.

## Goals

1. **One place for what needs a person.** A Needs me view collects review requests, help requests, stale work and unseen changes, with the action for each right there.
2. **Review that Beads itself enforces.** Built on human gates, so an agent working from the CLI is held by the same rule as one working through Abacus.
3. **Trustworthy history.** See every past state of a bead and put a field back.
4. **Edit the context agents start from.** Project memories, which every agent session in the project receives.
5. **Close the editing gaps** for fields and actions Beads supports and Abacus does not.
6. **Live updates on Beads 1.3**, without changing a project's Beads config silently.

## Non-goals (0.2)

- Query bar and saved searches (backlog 27), context preview before attaching (7), notifications (9), bulk actions (16), the full-screen board (34), `bd serve` adapter (38). They stay in the backlog.
- Per-bead keep mine / take theirs conflict resolution. Beads 1.3.1 now settles same-field edits last-write-wins on its own; Phase 0 already tells the user when an older edit was replaced. Delete-versus-edit conflicts keep the 0.1 "Hand to agent" path.
- Formulas, molecules, swarms, wisps.
- Enforcing anything Beads does not enforce. Abacus shows what happened; it does not police agents.

## Anti-goals (failure even if it technically works)

All 0.1 anti-goals stand: stale data, missing context, hard to read or use, a silent config change, `--force`, pushing without the user's click. New for 0.2:

1. **A noisy inbox.** If Needs me fills with items that do not need the person, it gets ignored. Every section must have a clear reason to be there and a one-click way out.
2. **Losing a memory.** Memories reach every agent session. An edit or a forget must be deliberate, confirmed when destructive, and visible in history.
3. **Undo that overwrites newer work.** Restoring a field must never clobber a change made after the one being undone.

## Constraints

### Beads versions

- **Primary target: bd 1.3.1.** The user's system bd was upgraded to 1.3.1 on 2026-10-14 (all projects backed up first). Phase 0 (in progress, separate lane) makes the existing 0.1 features work on 1.3.1.
- **bd 1.2.2 keeps working** for everything 0.1 does. New 0.2 features use commands that exist in 1.2.2 too (gates, `bd human`, `bd history`, memories, `bd stale`, `bd defer`, `supersede`, `duplicate`, `bd epic`, `bd ready --explain`) unless noted. Live updates need 1.3 and are hidden on 1.2.2.
- Facts are in `docs/bd-cli-contract.md`, including the "bd 1.3.1 differences" section. Notable for 0.2: the events table is clone-local on 1.3 (Activity only names changes made on this computer), embedded commit messages no longer carry the actor, `bd update --status <done>` enforces close policy, reassigning a bead someone else holds in progress is refused.
- Never pass `--force`. Never run `bd config set` without the user pressing a button that says what it will do.

### Host

Unchanged from 0.1 (`docs/sdk-contract.md`): sandboxed iframe with `allow-scripts` only (no forms, no popups, no modals), host toasts, chip attach, session start, a worktree start closes the panel, no API to list sessions by linked item.

## Experience

### 1. Gates (the shared base)

A gate is a Beads issue that blocks another bead until it is resolved. `bd close` refuses to close a bead while a blocker is open, so a human gate holds the bead closed for agents and people alike.

- **On a bead's detail**, a "Waiting on" block lists open gates that block it: title or reason, type (`human`, `timer`, `gh:run`, `gh:pr`, `bead`), who created it and when. Resolved gates appear in History, not here.
- **Resolve** (human gates only): a button with an optional reason, `bd gate resolve <gate-id> --reason`. Timer and GitHub gates are read-only with their state.
- **Request review**: an action on a bead ("Review before closing") creates a human gate, `bd gate create --type=human --blocks <id> --reason "<text>"`. The default reason is "Review before closing"; the person can edit it.
- **Approve plan**: the same mechanism with the reason "Approve the plan before work starts". **My call:** plan approval is a human gate with a known reason prefix, not a new field or status, so agents can create the same gate from the CLI and Abacus recognizes it. The plan itself lives in the bead's Design section.
- **Gate beads are hidden** from the Epic and Status lists (they have type `gate` or are recognized via `bd gate list`) and shown only on the beads they block and in Needs me.
- **Audit flag:** when a gate is resolved by an actor other than this panel's actor, the Activity row and the bead's History say so plainly ("Review gate resolved by Claude Code"). Agents can resolve gates from the CLI; Abacus makes that visible.

### 2. Needs me

A new first view next to Epic, Status and Activity, labelled "Needs me" with a count. **My call:** it becomes the default view when its count is above zero on opening a project; otherwise the last used view opens, as today.

Sections, in this order. A section with nothing in it is not shown.

1. **Waiting for your review.** Beads blocked by an open human gate. Actions: open, Resolve gate, open the bead's history.
2. **Asked for help.** Beads labelled `human` that are not closed (`bd human list`). Actions: Respond (a comment, then close, `bd human respond`), Dismiss (`bd human dismiss`), open.
3. **Stuck.** In progress with no update for N days (`bd stale --status in_progress --days N`), plus, on 1.3, claims whose lease expired. N defaults to 3, set in the panel's settings for the project. Actions: Keep (hide from this section for 7 days, stored in panel storage, no Beads write), Defer (`bd defer --until`), open.
4. **Changed since you last looked.** The existing unseen set, grouped by bead, newest first. Actions: open (marks seen), Mark all seen.

Each row shows why it is in the section (gate reason, the help request text, "No update in 5 days", "Priority P1 → P0 by Claude Code"). The rail badge keeps its 0.1 meaning (unseen beads). **My call:** keep the badge as is to avoid changing a learned signal; the Needs me count is shown on the view tab.

### 3. History and undo

- **History on a bead's detail**: a section listing past versions from `bd history <id>` (commit snapshots; on 1.3 `--events` adds audit events where present). Each entry shows when, who (when known), and which fields changed with before and after values. Long text fields show a compact diff.
- **Restore a value**: on a field change in History or on an Activity row, "Restore previous value" writes the old value back through the normal write path (re-read before write, with `expected` set to the value the change produced). If the field has changed again since, the restore is refused with the current value shown, and the person decides. Anti-goal 3.
- History is read on demand when the section is opened, not polled.

### 4. Project memories

- **Where:** a "Memories" entry in the panel header menu opens a full-panel page for the current project. **My call:** a page, not a view tab, because it is about the project rather than its beads.
- **Shows:** every memory (`bd memories`), with its key and text, newest first, and a search box. A line at the top says "Every agent session in this project starts with these."
- **Add:** text plus an optional key, `bd remember "<text>" [--key <key>]`.
- **Edit:** `bd remember "<new text>" --key <existing key>` (bd updates in place).
- **Forget:** confirm with the memory's text shown, then `bd forget <key>`.
- Writes go through the same re-read-before-write path as bead edits (read the memory again; refuse with a notice if it changed since the page loaded).
- Anti-goal 2: a forget is never one click; an edit shows the old text until saved.

### 5. Editing gaps

- **Due and defer dates.** Edit in the detail's More section. Input accepts what bd accepts ("tomorrow", "next monday", "+2d", ISO) with a preview of the parsed date before saving. Defer with a date uses `bd defer --until`; "Defer indefinitely" and "Undefer" are explicit actions. New filters: Overdue, Due this week.
- **Move and retype.** Change parent (pick an epic, or "No parent") and type after creation, from the detail header.
- **Acceptance checklist.** `- [ ]` items in Acceptance criteria become tickable in the detail. A tick rewrites only that line through the normal write path. Beads with no acceptance criteria show a quiet "No acceptance criteria" hint on the detail (not in the list).
- **Supersede and duplicate.** In the bead's menu: "Superseded by…" and "Duplicate of…", each with a bead picker, `bd supersede <id> --with <new>` / `bd duplicate <id> --of <canonical>`. Both close the bead; the confirmation says so.
- **Comment and close.** The close dialog gets an optional comment field; the comment is added first, then the close.
- **Why ready or blocked.** On the detail, a short line explains the state from `bd ready --explain`: which blockers or gates, or the defer date.
- **Epics ready to close.** When every child of an epic is done, the epic shows "All children done" with a Close epic button (`bd epic status --eligible-only` to find them).

### 6. Live updates (Beads 1.3)

- If the project's events journal is on, the service follows it (`bd events tail --since <seq> --follow`) and refreshes on each event instead of the polling signal check. Polling stays as the fallback and on 1.2.2.
- If it is off, the project settings show "Live updates are off for this project" and a button "Turn on live updates" that explains what it does ("Beads will keep a local log of changes on this computer for 7 days") and runs `bd config set events-journal true` only when pressed. Never automatic.
- **My call:** the journal is clone-local. (Superseded by Amendment 7: the setting is written to the tracked `.beads/config.yaml`, so it reaches teammates if committed, and the button copy says that instead.)

## Architecture notes for the builder

- New service routes (shared/api.ts): `gates`, `gateCreate`, `gateResolve`, `human` (list, respond, dismiss), `stale`, `history`, `memories` (list, remember, forget), `defer`, `supersede`, `duplicate`, `explain`, `epicEligible`, `eventsStatus`, `enableEvents`. Same patterns as 0.1: per-root queue, re-read before write, `--actor "<name> (panel)"`, typed errors mapped to plain messages.
- The snapshot gains: gate links per bead (or a gated set), the human-labelled set, the stale set, and the epic-eligible set, so Needs me renders from one snapshot without extra calls per row. History and memories are on demand.
- Version detection already exists (`bd --version` in workspace detection); expose a capability set (`eventsJournal`, `leases`) to the panel.
- Copy rules unchanged: no em dashes, "Beads" the product and "beads" the issues, no CLI words (pull, push, remote, dolt) in the UI.

## Development and verification

- Build in a worktree on a `feat/0.2` branch, so the installed extension (running from the main checkout) stays stable until merge.
- Spec, then plan, then build with subagents and per-task review, as in 0.1.
- Unit tests for every route and view; integration tests against real bd 1.3.1 in scratch projects; a live pass in OpenChamber on scratch copies (the pantry demo and a migrated copy of the shared project), with screenshots in `docs/verification.md`.
- Never run bd in real projects during development.

## Decided by the user

- Scope: the Beads gaps (gates and `bd human`, history, stale work, memories, due and defer, move and retype, supersede and duplicate, epics ready to close, why ready or blocked) plus live updates on 1.3. Query language deferred.
- Human gates as the base for review and plan approval.
- Upgrade to bd 1.3.1 and adapt (done for the system bd; Phase 0 in progress).
- Rolling solo for now; teammates will upgrade before they re-engage.
- Spec written without a question round.

## My calls (flag any you disagree with)

1. Plan approval is a human gate with a known reason, not a field or status.
2. Needs me becomes the opening view when it has items; the rail badge keeps meaning "unseen beads".
3. Stuck threshold defaults to 3 days, per project setting; Keep hides for 7 days in panel storage, with no Beads write.
4. Memories live on a page from the header menu, not a view tab.
5. Gate beads are hidden from the Epic and Status lists.
6. Live updates are opt-in per project with an explicit button.
7. A tick in the acceptance checklist rewrites only that line.
8. Build on a `feat/0.2` branch in a worktree.

## Left to the builder

Exact layouts and spacing (designer), the order of rows within sections beyond what is stated, how the history diff renders long text, debounce and backoff for the events follower, and the shape of the new snapshot fields.

## Risks and open questions

- `bd history` output shape and cost on large projects (verify on a scratch copy of the shared project; cap entries and page).
- Whether `bd memories` has JSON output in 1.3.1; if not, parse the text or read the `kv.` keys directly (verify).
- Gate visibility: confirm how gate beads appear in `bd export` (type, dependency kind) so they can be hidden reliably.
- `bd ready --explain` JSON shape and whether it can be scoped to one bead.
- Events journal follow inside the host service (a long-running child process): lifecycle, restarts, and the panel being hidden.

## Amendments from planning (2026-10-14)

The plan's bd 1.3.1 spike (`test/fixtures/bd13/`, contract section "bd 1.3.1 capabilities for 0.2") settled these. Where they differ from the text above, these win.

1. **Derived sets instead of per-poll routes.** Gates, the human set, the stuck set and epics ready to close are computed from the export the service already reads. The `gates`, `human`, `stale` and `epicEligible` routes are not built; integration tests check the derived sets match bd's own answers. `bd stale` is not used (it also rejects `--days 0`).
2. **"Gated"** means an open `blocks` edge to a gate whose status is not closed; a closed gate's edge stays on the bead. Gate rows (`issue_type: "gate"`) are excluded from every count and list.
3. **History** dedupes bd's one-row-per-commit output and joins `--events` for actor and label changes, capped and paged. On 1.3 the events table is clone-local, so an actor for another computer's change can be unknown; the copy says so instead of guessing.
4. **Memories** order comes from the config table's history (`bd memories` has no timestamps). Every write passes `--key`; a key named `schema_version`, or text equal to an existing key, is refused with a plain message.
5. **Defer indefinitely** clears the date first, then defers. **Date preview** uses a small parser of common forms and says "Beads will read this" for anything else.
6. **Gate resolve and human respond/dismiss** print text, not JSON: success is the exit code plus a re-read.
7. **Live updates button:** `bd config set events-journal true` edits the tracked `.beads/config.yaml`, so the confirm text says it changes a project file that may be shared if committed.
8. **Leases** (1.3) only exist for `--claim`, last 5 minutes, and are shown as a reason on a Stuck row, not as their own section.
9. **Where settings live:** a project menu in the panel header holds Memories, the Stuck threshold and Live updates. **My call:** Keep is stored per project.

## Success

The user opens a project after agents worked alone and, from Needs me, can see in under a minute what is waiting on them, resolve a review, see exactly what an agent changed and put back anything wrong, and adjust what every agent session starts with, without touching the `bd` CLI.
